The idea· one framework, one app

One framework. One app. Three functions.

An app is one struct. Its fields are its state.

__init__: the state it starts with.

update: something happened, so change the state.

view: describe the screen from the state.

The button sends TAP. Back to update. That's the whole loop.

The GPU· how the best apps do it

A typical GPU app: three languages meet.

The pattern behind scientific viewers, video tools and NVIDIA's own samples: C++ for the app, CUDA C++ for the kernel, GLSL for drawing, and interop so the picture never leaves the GPU. The cost is three languages, two compilers, and another kernel for GPUs that aren't NVIDIA.
The GPU· C++, CUDA, OpenGL

Two GPU languages…

The kernel is CUDA C++, compiled by nvcc. NVIDIA only.

Each thread works out its pixel from block and thread indices.

It writes one pixel.

Drawing it is a shader, in GLSL, compiled by the driver.

…and C++ to join them.

Once: share an OpenGL buffer with CUDA.

The GPU· an honest check

Do the best apps draw with the GPU? Yes.

Games, Blender and Figma draw their whole interface with the GPU.

Zed, a code editor, draws every letter with GPU shaders. Chrome paints web pages on the GPU.

Even plain toolkits do: GTK 4, Apple's Core Animation and every browser put windows together on the GPU.

So drawing with the GPU isn't what's new here. Writing for it is.

It would be wrong to say GPU apps don't draw with the GPU: the best known ones draw everything with it. What differs is how many languages and build steps it takes, and whether the same code runs without that GPU.
The GPU· in omxcode

In omxcode: one language, top to bottom.

Three flows: the web today, where the picture is copied to main memory; Linux with NVIDIA and the Mac, where every GPU app's picture stays on the GPU (D-5310, D-5311); and the same function on the CPU.

Where the others win, say so: their pixels never leave GPU memory on every platform, and Metal runs on every Apple GPU. omxcode's pictures stay on the GPU on Linux with NVIDIA (into a GL texture) and on the Mac (into an IOSurface Core Animation shows: no copy at all, since the Mac's CPU and GPU share one memory). What's new· agents build screens

Agents answer with native screens.

The other direction: an omxcode app is an AG-UI client.

The agent answers with a screen as data, from a catalog of 38 components.

The app checks it and draws it with real widgets.

No HTML, no code from the agent. Anything outside the catalog is refused, and the agent is told why.

A map, a timeline, a chart and buttons, all sent as JSON and drawn by the components an app uses. Tapping Book tickets goes back to the agent as the tool's result. Checked against Pydantic AI and LangGraph; docs/ag-ui-compatibility.md has a command for each claim.
What's new· agents build screens

The screen builds while it streams.

The agent's JSON arrives in pieces.

A tolerant reader draws whatever has arrived. Parts not here yet show a skeleton.

An approval waits for a person. The answer goes back to the agent.

Every cut of a streamed tool call, at every byte, either parses or waits; a test checks it never crashes. The agent's thinking shows live and then folds away.
What's new· agents build screens

A million rows. None sent by the agent.

The agent names a dataset the app already holds.

The app binds a grid to it. The rows stay in the app, queried by its own engine.

Pictures work the same way: the agent names one; it never sends pixels or links.

This is what an in-process framework makes possible: the agent describes; the app's own engine does the data work, next to the screen.
What's new· no boundary

An agent in the app's own process.

A LocalAgent is any Mojo struct with one method.

Given a run, it answers with AG-UI events.

No HTTP, no other language, no server to start. Its events go through the same handler as a remote agent's.

What's new· built in

It doesn't hang. By design.

update() and view() only decide.

Anything slow is a request, a timer or a job, on another thread.

Its answer comes back to update() as an ordinary event.

State is only touched on the UI thread: no locks, no races in app code.

Http.getApp.everystart_ui_job

Five rules, for a person or an agent writing an app: docs/ui-threads.md.

Network calls, file opens, queries, video decoding and exports all run off the UI thread, and a finished job wakes the window at once. An idle app uses no CPU.
