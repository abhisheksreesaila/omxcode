Why omxcode · measured, counted, every loss stated

One particle field, four ways.

The same app, up to twenty million particles pulled by your pointer, built in plain JavaScript, JavaScript + WebGPU, JavaScript + Rust, and omxcode. Then measured on one machine, counted line by line, and handed to an agent. Where omxcode loses, this page says so.

20Mparticles, the largest size tested, with omxcode's frames averaging under 16.7 ms (60 fps) and the slowest one in twenty under 20 ms. Measured with vsync off on a virtual display, not a real screen. JS + WebGPU and Rust + wgpu (native, offscreen) do it too.
257app linesin 1 Mojo file for omxcode, plus 164 framework lines (and 88 test lines) this goal added for it: PointCloud's step and draw, reusable by any app. JS + WebGPU: 522 lines, 8 files, 5 languages. JS + Rust is two apps: 374 lines, 10 files, 8 languages for wasm; 771, 6 and 3 for native.
5.33msan omxcode frame at 1M. JS + WebGPU takes 1.29 ms and native Rust + wgpu (offscreen) 0.34 ms: omxcode is slower, and the page says why.
1 · Performance

JavaScript runs out of frames. The usual fixes add languages.

Every build follows one spec (showcase/SPEC.md) and matches the same NumPy reference within 1e-3 after 120 steps.

How they were written: each by its own agent from its stack's official docs, under a contract that said not to read the other builds. Git can't show what an agent read; it shows that JS + WebGPU, omxcode and JS + Rust were committed at 22:57, 22:58 and 23:24 on 27 October, each commit touching only its own folders (omxcode's also the framework and one test), all before any measurement. A reviewer then looked for performance mistakes in each, and every build got fixes: JS + WebGPU stopped waiting on the GPU every frame; omxcode's skip of saturated pixels was modelled on JS + WebGPU's, and JS + WebGPU later got omxcode's load-first form of it; JS + Rust got its own thread-count probe and a cold start counted from the browser's launch.

The problem

Plain JS drops frames as N grows

One thread steps every particle and paints every pixel. At 100k particles it keeps up (3.55 ms a frame). At 1M its average frame still fits (14.26 ms), but it stutters: the slowest frame in twenty takes 23.3 ms. At 2M a frame takes 25.16 ms on average: it can't keep 60 fps, and it only gets worse from there. It is single-threaded on purpose: it is the "JavaScript alone" baseline.

The usual fixes

Move the work, add a language

  • WebGPU: two languages, JavaScript and WGSL shaders, joined by hand-packed buffers.
  • Rust → wasm: three or more languages, generated bindings, threads behind special headers, and a boundary crossed every frame: each particle is uploaded from wasm memory to the GPU.
  • Native Rust + wgpu: fast, but a second build with its own window code and no widgets.
omxcode

One Mojo file, native

The step is a Mojo function that runs as a GPU kernel; the slider and the readout are native widgets in the same file. One language, one build, a native window on Linux.

The four builds at one million particles

Each build's own screenshot from its correctness check, at 1M particles; the frames are not the same moment, and each draws its glow its own way (below). The readouts in the shots come from those checks, not from the measurement. The native Rust build draws the same field, its readout in a 3×5 bitmap font (its shot).

What the measurement says

JS + WebGPU, Rust + wgpu (native, offscreen) and omxcode (Mojo) hold 60 fps up to 20M (the largest size tested); JS + Rust/wasm holds 60 fps up to 5M; Plain JS (CPU) holds 60 fps up to 100k.

The fastest frame: Rust + wgpu (native, offscreen) at 1M (0.34 ms); JS + WebGPU at 5M (1.35 ms); JS + WebGPU at 20M (3.26 ms).

  • Rust + wgpu (native, offscreen) is faster than omxcode at every size measured (0.34 ms against omxcode's 5.33 ms at 1M; 5.97 against 7.63 ms at 20M). Native Rust renders offscreen here and never presents to a window (see the caveats), so its frame skips the window system the others pay for.
  • JS + WebGPU is faster than omxcode at every size measured (1.29 ms against omxcode's 5.33 ms at 1M; 3.26 against 7.63 ms at 20M).
  • omxcode is faster than JS + Rust/wasm at 5M, 10M, 20M and slower at 1M, 2M (2.06 ms against omxcode's 5.33 ms at 1M; 55.72 against 7.63 ms at 20M).
  • omxcode is faster than Plain JS (CPU) at every size measured (14.26 ms against omxcode's 5.33 ms at 1M; 220.01 against 7.63 ms at 20M).
  • The GPU step itself is a tie. At 20M it takes 0.770 ms in JS + WebGPU, 0.771 ms in Rust + wgpu and 0.763 ms in omxcode: the same arithmetic on the same GPU, within 1 % of each other.
  • Where omxcode's frame goes. At 20M its GPU work is 2.81 ms (step and draw) plus 0.42 ms copying the finished picture to the CPU; with one wait a frame that is 3.35 ms. The other 4.28 ms of its 7.63 ms frame is inferred, not measured: the frame minus that work. We read it as the GTK host taking the picture as a texture and compositing it (here with GTK's software renderer on a virtual display), because it hardly depends on N: the same residual is 4.31 ms at 1M and 4.28 ms at 20M, 20 times the particles. The copy and that path, not the GPU, are what make omxcode slower today; drawing straight from the GPU into the window is not built yet.
  • omxcode's frame is noisy. Its spread across the three runs is up to ±1.22 ms, and its 2M figure (4.44 ms) is below its 1M one: read its line as flat within that noise.
  • Start and memory. At 1M, cold start to the first drawn frame: Rust + wgpu (native, offscreen) 257 ms, omxcode (Mojo) 325 ms, JS + Rust/wasm 1,008 ms, Plain JS (CPU) 1,026 ms, JS + WebGPU 1,197 ms. Native Rust has no window or swapchain to make, as it renders offscreen. Peak memory (the process tree's PSS, so pages Chromium's processes share count once; GPU memory not included): Rust + wgpu (native, offscreen) 171 MB, omxcode (Mojo) 236 MB, JS + WebGPU 620 MB, Plain JS (CPU) 652 MB, JS + Rust/wasm 856 MB. The browser rows carry Chromium itself in both.

One fix cost JS + WebGPU time. For even-handedness the reviewer asked that it skip saturated pixels the way omxcode does (look first, then add). Measured through the same gate, that form is slower for it at large N: 1.70 and 3.26 ms at 10M and 20M here, against 1.51 and 2.67 ms with its own add-first form in the previous gated run (commit 349eb23). Every caveat, from the measurement itself

In the measurement's own words: A = JS + WebGPU, A-cpu = plain JS, B = JS + Rust (B-wasm in the browser, B-native the wgpu window), C = omxcode.

  • A draws with an atomic compute rasteriser (two u32 atomics per on-screen particle): it loads the pixel's count first and skips both atomics once the pixel is saturated (past the tone map's white for the dimmest channel), as C does; its look is a tone map, not the SPEC's clamp. ?render=points (hardware point blending) exists and is not measured here.
  • C's splat is the framework's generic PointCloud.splat: three u32 atomics per particle (r, g, b), each skipped once that channel's sum is saturated (an atomic load first; exact: the GPU still matches the CPU path). That skip was modelled on A's (a fair-play fix after review); A then got C's load-first form, so both skip the same way.
  • B draws with hardware blending (WebGL2 points / wgpu point list, additive). B-wasm steps on the CPU (wasm SIMD + a rayon pool in a worker) and uploads one packed u32 per particle to the GPU every frame.
  • C copies its finished picture (1280 × 720 × 4 bytes) from the GPU to the CPU every frame and hands it to GTK as a texture: that is the framework's Canvas path today. readback ms is that copy alone, measured on the separate pass.
  • C's step ms comes from a separate timed pass after the measured frames (Mojo 1.1's DeviceEvent has no elapsed time; the frame loop waits for the GPU once a frame, so it can't split step from splat).
  • C runs in the real GTK host on Xvfb, where GTK composites with its cairo (software) renderer; on a real display GTK uses its GL renderer. A and A-cpu run in Chromium on the same Xvfb display (ANGLE/Vulkan, no Vulkan surface).
  • C's frame clock is capped at 60 fps by GTK unless GDK_DEBUG=no-vsync (verified: 16.7 ms at every N with the cap, 4.8 ms at 1M without), so its headline is measured uncapped.
  • A's headline comes from &await=0 with the queue drained at the warm-up's end: Chromium's onSubmittedWorkDone round trip (5-9 ms here) would otherwise dominate, and the rAF interval alone runs ahead of the GPU. So A's p95 is a rAF interval that runs ahead of the GPU: for A the p95 test never binds, the throughput figure does.
  • A's CPU encode reads 0.100 ms at every size: Chromium clamps performance.now() to 100 µs on a page that isn't cross-origin isolated, so it means 'under about 0.1 ms'.
  • B-wasm's thread count was chosen by its own probe (every core, and cores - 2, one run each; the faster used).
  • B-native renders offscreen only (NVIDIA's Vulkan driver can't present to Xvfb), two frames in flight: it never presents to a window here, so its frame, cold start and memory have no window or swapchain in them.
  • B-wasm runs in headless Chromium (no Xvfb), WebGL2 through ANGLE on NVIDIA's EGL (OpenGL), the fastest path found.
  • A-cpu is single-threaded by design (plain JS on the main thread, the 'JS alone' baseline); it uses no GPU for the step, and Chromium composites its canvas.
  • Peak memory is the PSS of the launched process tree (Chromium's processes, or the one native process), from smaps_rollup every 100 ms: a page shared by several processes counts once in all. RSS (every 20 ms) is in results.json too; it counts a shared page once per process, which inflates the multi-process browser rows. GPU memory is not included. C keeps a CPU copy of all points (16 bytes each) by design of PointCloud.
  • Cold start includes each runtime's own start: Chromium's for A, A-cpu and B-wasm; the GPU driver's for all.
  • The machine has two RTX 3090s; each runtime picks its own (all report an NVIDIA GeForce RTX 3090). Each run's 1-minute load and the GPU's compute apps at its start are in results.json.

3 · The agent's view

What the agent has to write, and how it uses what it built.

Agents write most new code now. Every language, binding and build step is something an agent has to get right, and something you have to review.

What it writes

Plain JS (CPU)

4 languages · 3 files · 2 build steps
CSSHTMLJavaScriptPython

No seam, and no GPU: one thread steps and draws every particle. Simple, and it runs out of frames first.

JS + WebGPU

5 languages · 8 files · 2 build steps
CSSHTMLJavaScriptPythonWGSL

Two languages meet by hand. A Params struct in WGSL must match a 32-byte buffer that JavaScript packs field by field (main.js 177); every buffer, pipeline and bind group is made in JavaScript, and remade when the count changes.

JS + Rust (wasm and native)

9 languages · 13 files · 10 build steps
BashCSSGLSLHTMLJavaScriptPythonRustTOMLWGSL

Rust in three crates, JavaScript around it, GLSL for the browser's draw and WGSL for the native one. wasm-bindgen writes the glue; JavaScript reads wasm memory through raw pointers and must re-take its view when memory grows. Threads need COOP/COEP headers, a worker (rayon blocks its caller), -Z build-std unlocked on a stable compiler, and a sed patch to a generated file. The native build repeats the step in WGSL and pads its structs by hand.

omxcode

1 language · 1 file · 3 build steps
Mojo

One Mojo file. The step is a Mojo function (advance) handed to the GPU as a parameter; the slider and the readout are widgets in the same view(). No glue, no second language, one build. It leans on the framework's PointCloud, which this goal extended (counted in chapter 2).

How it uses the running app

The browser builds, and native Rust

  • In a browser an agent drives the page from outside, through a browser tool: screenshots (about 1,600 tokens each for a vision model, measured here) or the page's accessibility tree (Playwright's MCP server reads it, for example). The tree gives it the slider and the readout; the canvas is pixels.
  • The native Rust window has no widgets and no accessibility tree: its readout is drawn by a shader and its count is keys 1 to 5. An agent gets pixels and keystrokes.
  • Either way the app itself offers nothing to an agent; you would write an MCP server beside it.

AG-UI: the agent sends data, the runtime builds the screen

Over AG-UI, an open event protocol, an agent calls one frontend tool, render_ui, with components from a catalog. omxcode checks it against the catalog's JSON Schema, refuses anything else (and tells the agent why), and draws native widgets. No component the agent can name runs code or loads a page.

The agent's render_ui call (scripts/agui_agent.py, the scripted agent the checks use)
