The vision

One framework for everything. Data apps first.

A serious app today is four programs: an interface per platform, data work on a server, graphics in a shader language, and an API for agents. omxcode makes them one Mojo program. We start where that pays most: apps that move a lot of data between the screen and the GPU.

One way to do each thing

Every app is two functions.

view() describes the screen. update() reacts to a tap, a key or an agent's call. Less to learn, and less for an agent to get wrong.

viewdef view(self) -> View:
    return Button("Tapped " + String(self.n),
                  on_tap=TAP)
updatedef update(mut self, e: Event):
    if e.message == TAP:
        self.n += 1
tap→update()→view()
MCP, built in

Every app is an MCP tool server.

Buttons, fields and JS widgets become tools, with no per-app work. A disabled button isn't a tool, so an agent can't do what a person couldn't.

The window never waits

Slow work runs beside the screen.

update() only decides. Queries, video decoding and OCR run as jobs on their own threads and come back as events. A watchdog names any frame over budget.

Why omxcode exists

Four reasons.

1 · No boundary tax

No JSON, no HTTP, no second process.

Nothing extra to start, keep alive and debug. Apps that move a lot of data between the screen and the computing are faster and simpler.

2 · One language

From pixels to GPU kernels.

Mojo writes the interface and the CUDA-class kernels. In omxplorer, the group-by kernel sits in the same codebase as the sheet that shows its totals.

3 · Agent-driven

Every app can be driven by an agent.

omxcode has an agent host, so each app can be operated by an agent through the same code that draws its screens. JS apps need that built in separately.

4 · Every device

Native on every device from one codebase.

Phone included. Linux and the Mac run today; Android runs on the emulator and iPhone builds, with phones next on the roadmap.

Where to start, and where not yet

Start with apps that move a lot of data: analytics, spreadsheets, video, documents, robotics. For forms, CRUD screens and marketing sites, JS wins today on ecosystem alone; when a JS library is the better tool, embed it as a widget inside omxcode. SaaS building blocks (sign-in, accounts, payments) are on the roadmap.
