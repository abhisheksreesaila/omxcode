Agent-native works today

A language agents are fluent in needs a framework they can ship with.

Ask for the next great language for agents and the wish list is short: as fast as Rust, little design space, the strictest types, every kind of hardware. Mojo is that language. omxcode is the framework that lets an agent turn it into a whole app.

The recipes are in the box. llms.txt and the component matrix tell an agent what exists and where it runs; every component has a test, and a lint keeps an app to components and theme roles, so what an agent writes stays small and right.

Proof, built by coding agents: the OMX Console, a 10-screen admin app of 4,400 lines of JavaScript, rebuilt from omxcode components only. The web build matches the original on ≥ 99 % of pixels on every screen at desktop and phone size; Linux and the Mac run it natively. omxplorer groups 1,000,000 rows on the GPU in the same process that draws them.

Agents works today

Agents don't click pixels. They call buttons.

Today, an agent uses an app the way a stranger would: Playwright or computer use, a screenshot, a guess at where the button is, a click, another screenshot to check. An omxcode app describes itself. Its buttons, fields, menus and lists are named tools the agent can call.

No per-app work. The agent is just another host, like GTK or the browser. A button's tag names its tool and its tooltip describes it. Every omxcode app is an MCP server already.

The screen is the permission model. A disabled button isn't a tool; a dialog's buttons exist only while it's open. An agent can't do anything you couldn't.

It answers in words, and costs fewer tokens. Each call returns what changed, in 60 to 650 tokens in omxplorer, where a screen-scraping agent spends about 1,600 on a fresh screenshot to see what happened. In omxplorer, read gives the grid's rows as text; render gives a picture, for agents that can see.

Running today: 29 components proven through the agent, with Claude Code or any MCP client over stdio (agent host). Agents build it too: one language from button to GPU kernel, docs as llms.txt.

One program works today

Everything in the same program.

Most data apps are a front end and a server that talk over the network. Mojo is the language of the interface, the data and the GPU code, so in omxcode they are one program.

1 language · 1 program · no API in between

And local apps? They skip the network, but most glue two or three languages together, and using the GPU means adding a second toolchain beside the app. In omxcode the GPU code is in the same file, and the rows go to the GPU once and stay there; each query sends back only its answer.

Live in the alpha on the desktop: omxplorer keeps 1,000,000 rows on the GPU and recomputes them in the same process that draws them. On the web, the same program runs on a server and the browser shows it, so there is a network hop until Mojo can build for WebAssembly. Next coming soon: an AI model in the same program too.

FAQ

Go on, ask.

Why build this at all?

Cross-platform used to mean the lowest common denominator: every platform had its own company and language, so "one codebase" meant a web page in a wrapper.

Path 1Agents write Swift, Kotlin and JS, and keep each app native.works, and that's fine
Path 2One systems language, small touches per platform, built for the GPU and AI.our bet ✦

Now agents write most of the code. We wanted to rethink it from first principles, and we use it ourselves.

Why Mojo?

Because one language can draw the interface, crunch the data, and one day run the model.

⚡ GPU native⚙️ systems speed🐍 reads like Python🧬 MLIR compiler🤖 Modular's AI kernels

Why not Rust?

Rust is great, but it wasn't designed around GPUs or AI. Mojo is being built for exactly that, right now, by Chris Lattner and Modular.

LLVMClangSwiftMLIRMojo

We'd rather stand on that giant's shoulders. Modular's take: Mojo vs. Rust.

Have you used it, or is it a claim?

We use it. Every day, on Linux, and every number on this page comes from a script.

Why "omxcode"?

It started as MX, for Modular, MAX and Mojo. Then we noticed MX is close to everything out there…

MXOh My, how do we solve this?omxomxcodeomxploreromxqua

"Oh My, how do we solve this?" So OM met the X, became omx, and we stuck it on everything. 🤷

What's coming next?

We're aiming at domains, not fixed apps. Each app goes wherever it leads.

For the framework: next tiles that snap, labels that fit · soon Mac and iPhone on hardware, AG-UI, an AI model in the same program.
