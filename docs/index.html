Agent-native works today

Mojo is the language agents are fluent in. omxcode is how they ship.

An agent's ideal language is as fast as Rust, strict, small, and reaches every kind of hardware. Mojo is that language. omxcode turns it into whole apps, and every app back into tools.

Little design space

Every app is two functions.

view() says what's on screen, update() what an event changes. Components, themes and effects do the rest, one way each, so there's less for an agent to get wrong.

viewdef view(self) -> View:
    return Button("Tapped " + String(self.n),
                  on_tap=TAP)
updatedef update(mut self, e: Event):
    if e.message == TAP:
        self.n += 1

Agents use apps

Agents don't click pixels. They call buttons.

Every button, field and list is a named tool, over MCP, with no per-app work. A disabled button isn't one: the screen is the permission model.

Agents build screens

Ask an agent. It answers with a screen.

Over AG-UI, the open agent–UI protocol, the reply is UI as data: native components, checked against the catalog before anything is drawn. Buttons and switches it built talk back.

Every screen, natively

One app. Each platform's own widgets.

AppKit on the Mac, GTK on Linux, HTML on the web, Android's views on Android; iPhone builds. Not a web page in a wrapper.

omxconsole on the Mac, Linux and the web · the gallery example on the Android emulator

The recipes are in the box. llms.txt and the component matrix tell an agent what exists and where it runs; every component has a test, and a lint keeps an app to components and theme roles.

Proof, built by coding agents: omxconsole's 10 screens rebuilt from components only, ≥ 99 % of pixels equal to the JavaScript original at desktop and phone size; omxplorer runs 100 million rows on the GPU.

One program works today

Everything in the same program.

Most data apps are a front end and a server that talk over the network. Mojo is the language of the interface, the data and the GPU code, so in omxcode they are one program.

1 language · 1 program · no API in between

And local apps? They skip the network, but most glue two or three languages together, and using the GPU means adding a second toolchain beside the app. In omxcode the GPU code is in the same file, and the rows go to the GPU once and stay there; each query sends back only its answer.

Live in the alpha on the desktop: omxplorer keeps 1,000,000 rows on the GPU and recomputes them in the same process that draws them. On the web, the same program runs on a server and the browser shows it, so there is a network hop until Mojo can build for WebAssembly.

Where this is going: the AI model in the same program as well, beside the interface and the data, on iPhone as on the desktop.

FAQ

Go on, ask.

Why build this at all?

Cross-platform used to mean the lowest common denominator: every platform had its own company and language, so "one codebase" meant a web page in a wrapper.

Path 1Agents write Swift, Kotlin and JS, and keep each app native.works, and that's fine
Path 2One systems language, small touches per platform, built for the GPU and AI.our bet ✦

Now agents write most of the code. We wanted to rethink it from first principles, and we use it ourselves.

Why Mojo?

Because one language can draw the interface, crunch the data, and one day run the model.

GPU nativesystems speedreads like PythonMLIR compilerModular's AI kernels

Why not Rust?

Rust is great, but it wasn't designed around GPUs or AI. Mojo is being built for exactly that, right now, by Chris Lattner and Modular.

LLVMClangSwiftMLIRMojo

We'd rather stand on that giant's shoulders. Modular's take: Mojo vs. Rust.

Have you used it, or is it a claim?

We use it. Every day, on Linux, and every number on this page comes from a script.
