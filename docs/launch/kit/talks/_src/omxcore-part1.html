This is omxcore, the data engine under everything I build. It runs SQL on your CPU and your GPU, over plain CSV and Parquet files, written entirely in Mojo. Why

Your GPU naps

Most workstations have one. Analytics engines run on the CPU and leave it idle.

Your data is in files

CSV and Parquet. Most tools want you to import them first, into their own format.

Agents can't squint

What it is

A library, like SQLite.

Not a server, not a database. It links into your app, or runs as one small program.

mx

a native command line: SQL in, JSON out. A cold run on a small file takes about 11 ms, process start included.

Python

a lazy dataframe API and SQL, one native call per .compute(). On PyPI as mxframe 0.6.0.

Mojo

a package, omxcore.mojoc, that an app vendors and links. That's how omxplorer uses it.

Exact decimals

A DECIMAL is a JSON number whose text is exact. Parse it with a decimal parser, never a float.

Positions

Line and column, 1-based, into the SQL text.

Refused by name

An unsupported form raises with its line and column. Malformed SQL never crashes (fuzzed).

Under the hood · the GPU kernel

The kernel reads the plan as instructions.

  • The planner compiles a statement into a few instructions a row; one kernel steps through them.
  • Group sums accumulate with monotonic atomics. Mojo's stdlib Atomic is sequentially consistent, which put fences around every add: about 100× slower.
  • Integer sums note overflow instead of wrapping.
@always_inline
def _atomic_add_f64[space: AddressSpace](
        ptr: Pointer[Float64, MutUntrackedOrigin, address_space=space],
        val: Float64):
    var v = __mlir_op.`builtin.unrealized_conversion_cast`[...](val)
    _ = __mlir_op.`llvm.atomicrmw`[bin_op = ..., ordering = `2 : i64`, ...](...)

# inside the grouped kernel: one instruction per aggregate
for a in range(A):
    var ins = code + (HDR + (agg_base + a) * 5)
    var kind = Int(ins[0])
    var v = rebind[Float64](regs[Int(ins[2]) * TILE + tid + k * B])
    if kind == OP_AGG_SUM:
        var p = faccs + (a * G + g)
        _atomic_add_f64(p, v)
    elif kind == OP_AGG_ISUM:
        _note_ovf(_atomic_add_bits(p, yv), yv, ovf)
mxframe kernels_aot/pipeline_gpu.mojo (lines 156–158, 975–985), trimmed · docs/lessons.md 2026-09-29
For the GPU people, real kernel code: the plan arrives as instructions, and the grouped kernel steps through them per row. One lesson: Mojo's standard Atomic is sequentially consistent, so every add got fenced, about a hundred times slower. We use an LLVM atomicrmw with monotonic ordering instead.
Exactness

Money is a scaled integer.

INT and DECIMAL

Exact scaled int64. Sums are exact 64-bit, and the checks compare to the cent. A sum past int64 raises rather than wrapping.

FLOAT64

Follows DuckDB: NaN equals itself and sorts last, −0.0 equals 0.0. Float sums run in a fixed order, so the bits are the same on any core count.

Correctness is judged against DuckDB, never against our own CPU path.

docs/omxcore-mojo-api.md (Exact integer arithmetic) · docs/mojo-engine.md "Types and exactness (F-157)" · docs/lessons.md 2026-09-30
Money and quantities are scaled 64-bit integers, so sums match to the cent, and an overflow raises instead of wrapping. Float sums run in a fixed order, so the bits are the same on any core count. And we check answers against DuckDB, never against our own CPU path.
