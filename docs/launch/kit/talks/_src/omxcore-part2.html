How you'd write a query · 1 of 3

In Python: lazy, then compute.

import omxcore as mx          # 0.6.0 on PyPI: import mxframe as mx

lf = mx.scan_parquet("lineitem.parquet")
out = (lf.filter(mx.col("l_quantity") < 24).groupby("l_returnflag")
         .agg(mx.col("l_extendedprice").sum().alias("revenue"))
         .sort("l_returnflag").compute(device="cpu"))   # a pyarrow Table
print(out.to_pandas())

One native call

Nothing runs until .compute(); then the plan is optimized and executed at once.

device=

"auto" (the default), "cpu" or "gpu".

Says why

explain(device="auto", costs=True) prints the plan and the device choice.

mxframe docs/reference.md (Quick start; examples run by tests/test_readme_api.py)
From Python it looks like Polars: lazy scan, filter, group by, aggregate. Nothing runs until compute; then the whole plan goes down in one native call. Pick a device or leave it on auto, and explain tells you why.
How you'd write a query · 2 of 3

In Mojo: no Python at all.

from omxcore import read_csv, CsvOptions, Query, Frame, col, lit, sum, count, AUTO

var csv = read_csv(String(argv()[1]), CsvOptions())  # parallel, typed, with an import report
var orders = csv.take_table().share()
var region = orders.column("region")
var groups = len(orders.dictionary(region))

var out = (Query(orders)
           .where(col("qty") > 2)
           .group_by(col("region"), groups=groups)
           .agg(sum(col("revenue")), count())
           .compute(AUTO))                          # CPU or GPU; out.device says which

var f = Frame(orders)                              # edits on top of shared data, no copy
f.set_text(f.column("revenue"), 0, "99.00")
f.formula("net = revenue - qty")
var total = Query(f).agg(sum(col("net"))).compute()

From Mojo there's no Python anywhere: read a CSV in parallel, build a query, compute on AUTO, and the result says which device ran it. Below that, a Frame: an editable layer over shared data, with formulas. That's what a spreadsheet app needs.
How you'd write a query · 3 of 3

Or SQL, from Mojo.

var cat = Catalog()
cat.add_table("orders", orders)              # a SharedTable
cat.add_frame("edited", frame)               # a Frame, snapshotted now
cat.add_scan("big", scan_parquet(path))      # a Parquet file, a row group at a time
var r = sql(cat, "SELECT region, sum(revenue) AS total FROM orders WHERE qty > 2 "
                 "GROUP BY region HAVING count(*) > 5 ORDER BY total DESC LIMIT 10")
r.table          # an owned Table: INT, DECIMAL, TEXT, DATE, BOOL and FLOAT
r.notes          # what the planner decided and what ran, one line each
var o = PlannerOptions(); o.group = GROUP_HASHED   # or GROUP_AUTO, GROUP_DENSE

The numbers

22 simplified TPC-H queries, SF10.

omxcore3.15 s
DuckDB5.08 s
Polars14.40 s

On the CPU. Query time only: each engine loads its columns first, outside the clock; one fresh process per query, no warm-up. Answers equal DuckDB's on the same simplified queries; Polars' Q1 is wrong. Not TPC-certified; a shared machine, so indicative.

Where Mojo pushed back

Four lessons, now in the code.

Threads flush denormals

parallelize runs tasks with flush-to-zero set, so threaded kernels read 5e-324 as 0. Workers launch only through one helper.

A list freed early

A List whose address goes into a kernel call is freed at its last use. After the third time, a check script fails the build.

Metal's private pointers

A pointer made from an integer is thread-private on Apple's GPU: writes vanish with no error. Kernels name the global address space.

Ordered compares

SIMD.ne is ordered, so NaN.ne(NaN) is False. NaN is tested with ~x.eq(x).

mxframe docs/lessons.md (2026-10-16 ×2, 2026-10-19, 2026-10-25) · scripts/check_list_lifetimes.py · kernels_aot/_fpenv.mojo
Four things Mojo taught us, each now enforced in code: threads flush denormals to zero; a list handed to a kernel is freed at its last use, so a script now fails the build; on Metal, integer-made pointers are thread-private; and SIMD not-equal is an ordered compare.
The honest edges

What it doesn't do yet.

mx sql runs on the CPU

--device gpu is accepted and the notes say it ran on the CPU. The GPU is there from Python and the Mojo builder. (F-191)

TPC-H Q11

A DECIMAL sum passes int64. 128-bit totals come next, then 22 of 22. (F-192)

Some joins are slower

SF1, informal: Q7 72 ms vs DuckDB 16, Q5 41 vs 13. A star-aware planner is next. (F-161)

NVIDIA first

The GPU path is validated on NVIDIA. Apple's GPU through Metal is checked on GitHub's virtual Macs, not real ones.

Informal numbers

Most engine timings come from a shared machine. The quiet-machine scoreboard hasn't run yet.

Refused, by name

WITH RECURSIVE, LATERAL, correlated NOT IN. Every step of a compound query is materialized.
