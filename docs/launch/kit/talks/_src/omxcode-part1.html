This is omxcode, a UI framework written in Mojo. You write two functions, view and update, and the same app opens with native controls on Linux, in the browser and on the Mac, which I check on GitHub's virtual Macs. Swift for the Mac, Kotlin for Android, JavaScript for the web. Or one toolkit that imitates them all.

Speed means a second language

Agents squint

AI agents drive apps through screenshots and pixel coordinates. Slow, and it breaks.

omxcode: one readable language from the button to the GPU kernel, and every app is already a tool server.

~/Projects/omxlabs/readmes/omxcode.md "Why"
A serious app today means a codebase per platform, then a second language the moment you need speed, glued on with buffers you pack by hand. And agents mostly use apps by reading screenshots. Mojo reads like Python and compiles to GPU kernels, so one language can cover all of it. That's the bet.
How you'd write one

An app is a struct: state, update, view.

from mojoui import App, Event, View, VStack, Text, Button, TITLE, CAPTION, PROMINENT

comptime GREET = 1   # a message is just a number

struct Main(App):
    var name: String
    var clicks: Int

    def __init__(out self):
        self.name = "Ada"
        self.clicks = 0

    def update(mut self, event: Event):
        if event.message == GREET:
            self.clicks += 1

    def view(self) -> View:
        var greeting = "Tap Greet" if self.clicks == 0 else "Hello, " + self.name + …
        return VStack(
            Text(greeting, style=TITLE),
            Button("Greet", on_tap=GREET, style=PROMINENT),
            spacing=20,
        )
  • update() changes state when an event arrives.
  • view() describes the screen from state: a tree of plain values.
  • The shape of Elm, SwiftUI and React.
  • def only, comptime constants, no @value: Mojo 1.1 as it is today.

This is the whole hello app. A struct holds the state; update changes it when an event comes in; view returns a tree of plain values. It's the Elm, SwiftUI and React shape. A message is just a comptime number, and the button says which number to send.

Messages are numbers

A widget never holds a closure. The host looks the message up in the current screen when the event arrives, so nothing leaks and nothing needs rewiring.

Same path everywhere

GTK, the web, Android and AppKit all call the same update().

A tap end to end: the native button fires, the host calls into Mojo, update runs, view builds the new tree, the diff compares. Out comes one patch: set this label's text. Widgets hold a message number, never a closure, so nothing leaks across the C boundary.

Under the hosts

Mojo ↔ C, with nothing in between.

# Mojo exports a C symbol: scalars only, never raises
@export("KGEN_CompilerRT_AlignedFree")
def aligned_free(ptr: Int) abi("C"):
    external_call["free", NoneType](ptr)
  • Across the line: scalars and (pointer, length) strings. Never a struct by value.
  • Exports are @export + abi("C"), and can't raise.
  • State C keeps: alloc(Layout[T].single()), leaked to C as an address, read back as a Pointer.
  • Linking a Mojo shared library needs -rpath '$ORIGIN'.
mojoui/hosts/mojo_rt.mojo · CLAUDE.md "Mojo rules that bite" (Mojo 1.1.0)
For the Mojo people: exports use at-export and abi C, can't raise, and only scalars and pointer-plus-length strings cross the line. State C keeps is allocated in Mojo, handed over as an address, and read back as a Pointer. These rules took a while to find; they're written down in the repo.

The GPU, in the same file

A plain Mojo function becomes a kernel.

def mandelbrot(x: Int, y: Int, w: Int, h: Int, p: Params) -> UInt32:
    """Colour of one pixel. p = (scale, centre x, centre y, max iterations)."""
    var cx = p[1] + (Float32(x) - Float32(w) / 2) * p[0] / Float32(h)
    var cy = p[2] + (Float32(y) - Float32(h) / 2) * p[0] / Float32(h)
    var zx = Float32(0)
    var zy = Float32(0)
    var i = 0
    var limit = Int(p[3])
    while i < limit and zx * zx + zy * zy < 4.0:
        var t = zx * zx - zy * zy + cx
        zy = 2.0 * zx * zy + cy
        zx = t
        i += 1
    …

# in the same struct, on a tap:
var gpu = self.gpu.render[mandelbrot](WIDTH, HEIGHT, self.params())
self.pixels = gpu.pixels.copy()

# mojoui/gpu.mojo launches it, one GPU thread per pixel:
ctx.enqueue_function[_pixels_kernel[f]](…,
    grid_dim=(ceildiv(width, 16), ceildiv(height, 16)), block_dim=(16, 16))
  • No CUDA, no shader language, no buffer packing.
  • The same function runs on the CPU (render_on_cpu), and the app checks the GPU's pixels match.
  • The picture goes to the platform's own image view.
examples/gpu/app.mojo · mojoui/gpu.mojo · real code, trimmed
Mandelbrot is an ordinary Mojo function: the colour of one pixel. Render takes it as a compile-time parameter, and mojoui launches it in sixteen-by-sixteen blocks, one thread per pixel. No CUDA, no shader language. The same function runs on the CPU and the app compares the pictures.
