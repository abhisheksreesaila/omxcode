What it is

A small server, and a console.

  • mxc, a command line, runs a daemon in front of MAX.
  • The daemon starts one max serve per loaded model, on loopback ports.
  • The console shows every model: state, memory, speed, logs, a benchmark and a notebook.
  • State lives in ~/.mxc/: models, key hashes, the request log.
docs/ARCHITECTURE.md · docs/USER_GUIDE.md "The console", "Where things are" (mst.db)
Two pieces. mxc is the command line; it runs a daemon in front of MAX, and the daemon starts one max serve process per model that's actually loaded. The console shows every model with its state, memory, speed and logs, plus a benchmark and a notebook.

Call it · curl

Plain JSON, OpenAI's shape.

curl http://127.0.0.1:11435/v1/chat/completions \
  -H "Authorization: Bearer $MXC_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model": "qwen2.5-0.5b",
       "messages": [{"role": "user",
                     "content": "Hello"}]}'
  • Your port, on loopback: 11435.
  • One key per app, revocable.
  • The model is picked by name; the daemon routes on it.
  • No key: 401. A model that isn't registered: 404, telling you to run mxc pull.
docs/USER_GUIDE.md "Call it" · lines rewrapped
The curl call is OpenAI's chat completions, unchanged. It goes to your own port, carries a key that belongs to one app, and the model field picks who answers. A bad key gets a 401; a model you haven't pulled gets a 404 that names the command to run.
Call it · any OpenAI client

Change one URL. Keep your code.

import os
from openai import OpenAI

client = OpenAI(base_url="http://127.0.0.1:11435/v1", api_key=os.environ["MXC_API_KEY"])
reply = client.chat.completions.create(
    model="qwen2.5-0.5b",
    messages=[{"role": "user", "content": "Hello"}],
)
print(reply.choices[0].message.content)

Four routes: /v1/models, /v1/chat/completions, /v1/completions, /v1/embeddings. Anything else is a 404.

docs/USER_GUIDE.md "Call it" (Python, with the openai package; routes)
From Python it's the official openai package with a different base URL, so whatever you wrote against the cloud keeps working. The API is four routes; anything else is a 404, which keeps the surface small.

docs/ARCHITECTURE.md "How a request travels" · mxconsole/gateway.py, supervisor.py
The stack. Your apps see one URL. Under it, the daemon: the gateway checks keys and routes by model name, and the supervisor starts and stops one max serve child per model. MAX does the serving on the GPU; the daemon just decides who runs and streams the answer through.

docs/ARCHITECTURE.md (daemon; params.py reads MAX's own request schema) · mxconsole/supervisor.py
A request for a sleeping model: the daemon checks the key, sees the model is cold, starts max serve, and streams tokens back. Callers arriving together share one start, and nothing unloads mid-answer. Fields MAX would reject are dropped and named in a reply header, but anything that changes the answer, like tools or a seed, never is.
Idle unload, and pin

Register many. Load what's called.

5idle minutes

The default keep-alive. Then the model unloads and its GPU memory is free; the next call loads it again.

mxc serve smollm2-1.7b --pin
  # never unloads
mxc serve qwen2.5-1.5b --keep-alive 10m
  # unloads after 10 idle minutes
mxc set qwen2.5-0.5b --pin
  # change it later (or --unpin, --keep-alive 1h)
docs/USER_GUIDE.md "Idle unload and pin" · docs/CLI.md (--keep-alive, default 5m) · supervisor.py
This fixes one server per model. Register as many as you like; each loads when called and unloads after five idle minutes, giving the memory back. Pin the one you use all day. The honest cost: the first call after an unload waits for the load.
Keys

One key per app. Stored as a hash.

mxc keys new my-app       # printed once
mxc keys ls               # lists keys, never the secret
mxc keys rotate my-app    # new key, old one stops working
mxc keys revoke my-app
  • Keys look like mst-… and are stored only as SHA-256 hashes, so each one is shown once.
  • One key per app means you can cut off one script without touching the others.
  • The console's own /admin routes answer only on this machine.
docs/ARCHITECTURE.md (keys.py) · docs/USER_GUIDE.md "Keys", "Where things are" · docs/CLI.md
Every app gets its own key, stored only as a SHA-256 hash, which is why you see it once. You can rotate or revoke one script's access without breaking the others, and the console's admin routes never leave this machine.

docs/USER_GUIDE.md "Securing it on your LAN" · docs/ARCHITECTURE.md (expose.py; LiteLLM removed in F-063)
For your phone or laptop, mxc expose runs Caddy on port 8443 with its own certificate authority. Caddy checks the key and passes the request straight to the daemon; only the four v1 routes are reachable. A LiteLLM proxy used to sit in between; it was removed after its supply-chain incidents.
