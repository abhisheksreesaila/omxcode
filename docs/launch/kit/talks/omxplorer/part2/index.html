1 · the fleet is a spreadsheet you touch

63,344 episodes you can sort, pivot and chart.

Not a file browser of recordings: the fleet itself is the table. A chart is a sentence you type; a pivot is three picks.

docs/goals/47-report.md beat 1, M0 (63,344 episodes, 13 labs), M3
Most robotics tools open one recording at a time. Here, the starting point is the whole fleet, as a spreadsheet: 63,344 rows, one per episode. You touch it like Excel: sort, filter, pivot by lab and outcome, type a chart as a sentence. That's how you find which episodes to look at.

2 · what it wrote

The SQL says JOIN LINKED.

SELECT fleet.episode, fleet.lab, fleet.task, fleet.clip, fleet.source,
       COUNT(*) AS closes
FROM fleet JOIN LINKED
WHERE fleet.success = 0 AND telemetry.gripper_event = 'close'
GROUP BY fleet.episode, fleet.lab, fleet.task, fleet.clip, fleet.source
HAVING COUNT(*) >= 2 ORDER BY closes DESC, episode
# mojoui/asksql.mojo · implied_sql()
if not join.lower().endswith("join"):
    raise Error('write "FROM <table> JOIN LINKED": the links decide the joins')
scripts/scenario.py ROBOT_SQL1 (aliases trimmed) · mojoui/asksql.mojo
Here's the SQL behind that question. Notice there's no ON clause: it says JOIN LINKED, which means follow the links a person made. The engine writes the joins out along the shortest chain of key links. If no link reaches a table, it refuses instead of guessing.
3 · documents in the same join

The paper is a card, linked like a table.

fleet.source = paper.file
  • every row names the DROID paper as its source
  • page 15 marked: "All DROID data is recorded at 15Hz"
  • read from the PDF's own text, not OCR
  • provenance, not a per-row join: the dataset has one paper
docs/goals/47-report.md beat 4, M5 (page 15)
Documents aren't attachments here; they're cards you link like any table. Every fleet row names the DROID paper as its source, so one key link marks the passage that says the data is recorded at 15 hertz. To be precise: the dataset has one paper, so this is provenance, the same page for every row. With per-row paperwork, like bills of lading, it's a real join.

This is my favourite idea. Cards from different tables or media don't connect until a person, or an agent, makes a link. You drag a column onto a card, and it asks: link these? Before you say yes, it shows how many values match: here 14 of 18 shipments appear in the video. Links come in three kinds: by key, by time, and by place.

Hold any card, and everything it isn't linked to dims. The linked cards lift, and a labelled line shows how they're connected: shipment id equals code, a key link. Let go and it settles back. You can always see why two things belong together.
4 · no schema in code

The robot story is four typed lines.

fleet.episode = telemetry.episode
fleet.clip    = episode.file
telemetry.t   ~ episode.t +0
fleet.source  = paper.file

typed into the Links panel; an agent can add the same lines as tool calls

A key link onto a video card plays the row's file. One onto a log slices it into lanes. A time link puts both on one clock.

docs/goals/47-report.md "Record it yourself" and "What the framework gained" (Links)
For the robot data, the whole model is four lines a person typed. The episode key, its video file, the shared clock, and its paper. Each link tells cards how to react: onto a video it plays the row's file, onto a log it slices out that episode's lanes. No schema in code.
4 · in the framework

A link is a value. Who made it is part of it.

# mojoui/links.mojo
# The rule (owner, 2026-10-30): cards from the same table are linked implicitly; across tables or modalities nothing
# connects until a Link exists, made by a person or an agent. An app may suggest one; it never joins on its own.

struct Link(Copyable, Movable, ImplicitlyCopyable):
    var kind: Int
    var a: End
    var b: End
    var by: Int  # BY_PERSON or BY_AGENT (an app's suggestion becomes a Link only when one of them confirms it)
    var scale: Float64  # TIME: b = a · scale + offset; PLACE: x → lon
    var offset: Float64
    # …

def match_count(a_values: List[String], b_values: List[String]) -> MatchCount:
    """How many of a's distinct values appear in b: what a person sees before confirming a key link ("12 of 14")."""
mojoui/links.mojo (trimmed) · a framework component: any omxcode app can use it
In code, a link is a small value: two ends, a kind, and who made it, a person or an agent. Time links carry a scale and an offset, so two clocks can line up. The match count is a plain function: it's what you see before you confirm. And it lives in the framework, not the app, so any omxcode app gets explicit links.

README.md "Measured" (RTX 3090) · docs/goals/47-report.md beat 6, M7 (583.9 ms)
There's no analytics server. The engine, omxcore, is linked into the app like SQLite and runs in the same process that draws the window, on your GPU or CPU, whichever it picks for the query. On the GPU, a chart over a million rows takes about 0.6 milliseconds on an RTX 3090. The 16.8 million telemetry rows load in about 0.6 seconds as a background job, and after that one episode slices out in about two milliseconds.

docs/goals/47-report.md (Result, M8) · docs/goals/41-report.md (framefeed) · docs/ui-threads.md (examples/jobwake) · open edge: a 100M-row median still waits ~0.7 s (README)
Queries, imports, video and exports run as jobs on their own threads; the answer comes back as an ordinary event. A watchdog prints a SLOW line for any frame over budget. Through the whole robot story it printed none at 50 milliseconds. One edge is still open: a median over 100 million rows in memory still makes the window wait.
