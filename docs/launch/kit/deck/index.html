The big idea. Most apps that matter are really four programs glued together: the interface, rewritten for every platform; the data work, usually Python on a server; the graphics, in a shader language; and now an API so AI agents can use it. Every line between them is a rewrite, a network hop, or another team. omxcode is one program in one language, Mojo, which reads like Python. We start with data apps, because that's where one language from button to GPU pays off most.

README.md "Measured" · one Linux machine, RTX 3090 (0.5–0.7 ms)
How it's built. An app is one Mojo struct: update changes state, view describes the screen. That's the Elm and SwiftUI shape. Each host draws the view with the platform's own controls: GTK on Linux, AppKit on the Mac. The same view tree becomes MCP tools for agents. The data engine, omxcore, runs on the GPU inside the same process, so a chart over a million rows takes about 0.6 milliseconds on an RTX 3090, with no server in between. The web runs today through a server; running on the visitor's GPU with WebGPU is next, then phones.
The UI thread

The UI thread only decides.

At 60 fps the UI thread has 16 ms a frame. Queries, imports, video and exports run as jobs on their own threads; the answer comes back as an event.

0

SLOW: lines at a 50 ms budget across the checked video, query and export sessions (headless, CPU drawing)

6µs

a video seek on its own decoder thread (open ≈ 40 µs); the newest seek wins

83ms

worst frame gap on a Mac during a 1.5 s job, down from 1,527 ms (GitHub's virtual Macs)

docs/goals/41-report.md · docs/ui-threads.md · D-792 · open edge: a 100M-row in-memory median still waits ~0.7 s (README)
Every platform draws on one thread, and at 60 frames a second it has 16 milliseconds. Anything longer freezes the window. The rule in omxcode: update and view only decide. Anything slow is a job with its own copy of the data, and its answer comes back as an ordinary event. No locks in app code. A watchdog prints a SLOW line for anything over budget. The checks run the video, query and export sessions at a 50 millisecond budget, headless with CPU drawing, and print none. One edge is still open: a median over 100 million rows in memory still makes the window wait about 0.7 seconds; that's next. Video has its own decoder thread. And on the Mac, giving jobs their own threads took the worst frame gap from a second and a half down to 71 to 83 milliseconds, measured on GitHub's virtual Macs. Real hardware is next.

docs/goals/41-report.md (links.mojo, asksql.mojo) · illustrative query; the app writes its own
Putting a video, a table and a PDF on one screen is easy. Knowing why they belong together is the hard part. So in omxplorer, cards connect only through links you make: by key, like the robot model; by time, so the video and telemetry share a clock; or by place, a box in the frame tied to a row. Each link shows how many rows match before you confirm it. Ask in words, and the SQL it writes says JOIN LINKED: the links you made, as a join you can read. README.md "Agent native" · docs/agent.md · EXPERIMENTS.md exp. 35 · tool names illustrative
The same view tree that becomes GTK widgets becomes MCP tools. A button's tag names the tool, its tooltip describes it, and calling it is tapping it. I write nothing per app. It's safe by construction: a disabled button isn't a tool, a dialog's buttons exist only while it's open. The agent can do nothing a person couldn't. And AG-UI the other way: an agent streams words and builds a chart or a form, drawn natively. One honest note: agents don't know Mojo yet; to write apps they read our docs. The tool names on the slide are illustrative; use the real ones from the recorded session.
