## Caveats

- Measured on a separate headless Hyprland (the owner's session was locked), not the physical monitor: output HEADLESS-1 1920x1080 @ 60.0 Hz paced by a timer, GPU-rendered (NVIDIA GeForce RTX 3090/PCIe/SSE2, /dev/dri/card1 through EGL/GBM), no scanout; the window and its pixels are real compositor frames, but there is no monitor latency in any number.
- A runs DuckDB-WASM inside the browser: wasm memory is limited to 4 GB, so 100M rows load compressed (and slowly); its load time and steps are what that limit allows.
- B's every change crosses a network hop (the page's fetch to the local FastAPI server): real, but local (127.0.0.1), so it is cheaper than any deployed server.
- C and D are native desktop programs (native only); A and B are web pages that run in any browser.
- D needs an NVIDIA GPU today (CUDA through MAX); Apple through Metal is later work.
- D computes on cents: a deliberate data-model choice (amount and cost become integer cents at load, on every core, counted in its load time; sums are exact integers, converted at the edge); A, B and C keep float64. Every build's answers match the reference within the SPEC's 1e-6 relative tolerance.
- Every build sorts the rows by day at load (SPEC allows reordering at load; the time is in each load figure), so a date range is a contiguous slice or prunable by zone maps.
- Shortcuts each build takes for the newest 50 rows: A stores the table day descending / id ascending so DuckDB's zone maps prune the date range and its top-N stops after the first row groups, KPIs and chart in one statement; B takes the date range's slice of its day-descending frame and finds the newest 50 with a hand-written growing-window search at the slice's start (round 2, as C), the group-by on Polars' streaming engine, orjson; C searches a growing window at the slice's end for the last 50 matching rows (hand-written, not plain Polars; its README records the plain forms' slower numbers); D finds the cut-off day from a per-day histogram its GPU group-by already makes (product × day), then the rows on the GPU. B's and C's searches and D's histogram are equivalent hand-made shortcuts (coordinator, 2026-10-28).
- D wakes its UI the moment a background job ends (mojoui.jobs, a framework feature for every app, D-771); the others redraw when their own event loops see the result.
- Chromium's flags for A and B are --ozone-platform=wayland --use-angle=vulkan --ignore-gpu-blocklist: the protocol's --enable-features=Vulkan was dropped because Chromium can't composite with Vulkan on Wayland (its window never updated on screen with it); WebGL is ANGLE on Vulkan on the RTX 3090 either way.
- Input-to-pixels starts when the harness writes the step to the build's driver: for A and B that adds the driver's hop into the page (a Chrome DevTools Protocol call, about a millisecond), for C and D a pipe into the app.
- The observer sees the compositor's frames (60 Hz here): every latency includes waiting for the next composited frame (0–16.7 ms) and is reported to the compositor's presentation timestamp, not to the photons.
- nvidia-smi is never polled while a step is timed (it can stall the GPU): GPU memory is sampled during load, warm-up and the untimed resets between passes.
